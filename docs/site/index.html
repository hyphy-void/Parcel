Prepare your accounts

You need GitHub and Cloudflare accounts. Enable R2, create a Zero Trust organization, and enable a Workers subdomain. Skip anything you already have. R2 may ask for a payment method; complete billing and plan setup yourself.

This guide is for new instances. To upgrade an existing Go, Pages, or V3 instance, use the repository’s migration and production deployment docs so that two services do not manage the same bucket.

The app defaults to a 9 GB storage quota and an 8 GiB file limit. R2 free allowances are shared across your account; storage, requests, and other buckets affect billing. The app quota is not a billing cap. See R2 pricing.

Create the app

Click the deploy button and follow Cloudflare’s steps to create your own GitHub repository and choose a Worker, D1 database, and R2 bucket. Keep the root directory at / and use Node 24.

Use npm run build as the build command and npm run deploy as the deploy command. The deploy script applies D1 migrations through the DB binding and writes the actual bucket name to R2_BUCKET_NAME.

Turn off “Enable preview builds.” Leave “Protect with Cloudflare Access” off on the deployment screen. Configure Access for administrator paths in the next section so that share links remain public.

Keep ACTIVE=false for the first deployment. A serverless_unconfigured response is expected until runtime configuration is complete. Do not share links before setup is finished.

Set up admin Access

Go to Zero Trust → Access controls → Applications and add a Self-hosted app. Use the HTTPS hostname you will visit; you can start with your own worker.your-account.workers.dev address.

Add all seven paths to the same app, rather than protecting the entire hostname: 

/admin
/admin/*
/login
/api/v1/auth/*
/api/v1/admin/*
/api/v1/uploads
/api/v1/uploads/*

Create an Allow policy. Under Include, choose Emails and enter the administrator email addresses. Enable One-time PIN or your own identity provider. Do not add Bypass or protect the whole hostname: the homepage and /s/* share pages must remain public.

Copy the app’s AUD and your organization’s Team domain, such as https://your-team.cloudflareaccess.com. Set them as ACCESS_AUD and ACCESS_TEAM_DOMAIN on the Worker. Keep ADMIN_EMAILS consistent with the policy; separate multiple addresses with commas.

Create R2 credentials

Go to R2 → Overview → Manage API Tokens → Create Account API token. Choose Object Read & Write and restrict access to this app’s bucket. Save the S3 Access Key ID and Secret Access Key as two Worker secrets.

R2_ENDPOINT is the account-level S3 API address in the bucket settings, such as https://ACCOUNT_ID.r2.cloudflarestorage.com, without a bucket name or trailing slash. The Worker’s FILES binding, R2_BUCKET_NAME, and credential scope must refer to the same bucket.

Keep the bucket private. Do not enable a public r2.dev URL or public bucket domain. Uploads and downloads use short-lived presigned URLs.

Save variables & secrets

Open Worker → Settings → Runtime variables and secrets. Save ordinary settings as variables. Check “Secret” for these three values:

  • SESSION_SECRET: an independently generated random value of 64 hexadecimal characters.
  • R2_ACCESS_KEY_ID: the S3 Access Key ID you just created.
  • R2_SECRET_ACCESS_KEY: its matching S3 Secret Access Key.
Generate a session secret 
node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"

Generate the session secret in your own terminal. Keep it out of Git, issues, screenshots, and webpages. Back it up securely and preserve it on later deployments; replacing it prevents existing password-protected shares from being unlocked.

At minimum, set PUBLIC_URL, ACCESS_TEAM_DOMAIN, ACCESS_AUD, ADMIN_EMAILS, R2_ENDPOINT, and R2_BUCKET_NAME. PUBLIC_URL must exactly match the HTTPS origin you visit, without a path or trailing slash.

Allow browser uploads

Open R2 → your bucket → Settings → CORS Policy → Edit. AllowedOrigins must exactly match PUBLIC_URL. The configuration tool below generates the JSON to paste.

Under Object lifecycle rules, add a rule to abort incomplete Multipart uploads after one day, scoped to the parcel/v3/ prefix. Do not add a separate age-based deletion rule for completed objects: the app’s Cron and D1 state coordinate expiration and deletion.

Check that Cron is */5 * * * *. On Free, keep WORKERS_PLAN=free and CLEANUP_BATCH_SIZE=1.

Check before launch

Set ACTIVE to true and deploy. Test the whole flow with a small file before opening your instance.

  1. Open /admin in a private window. It should show Access login. An unauthorized email must not reach the admin page.
  2. Sign in as an administrator, upload a file, and create shares with and without a password.
  3. Open shares while signed out. Test correct and incorrect passwords, downloading, and Range resume. Refreshing a valid download session must not consume another download.
  4. Revoke a share and check that it cannot issue new signed URLs. Previously signed URLs can remain valid for up to five minutes.
  5. Wait for Cron. Confirm that quota is released after object deletion, and inspect Worker errors and CPU metrics.

Workers Free has a CPU budget of 10 ms per request. Local tests do not verify production CPU, Access, or real R2 settings. Check metrics if production returns error 1102. See Workers limits.

Need a hand?

The page returns serverless_unconfigured

Check the six ordinary variables and three secrets. SESSION_SECRET must contain 64 hexadecimal characters. PUBLIC_URL and R2_ENDPOINT must be HTTPS origins without a path or trailing slash.

host_denied or a login loop

The hostname you visit must match PUBLIC_URL. The Access app hostname, AUD, Team domain, and admin emails must belong to the same instance. When changing the production domain, update Access, PUBLIC_URL, and R2 CORS together.

CORS rejection or a signature error

Check that the CORS origin exactly matches PUBLIC_URL and that the FILES binding, R2_BUCKET_NAME, and S3 credential scope use the same bucket. An API token cannot replace the S3 Secret Access Key.

How do updates preserve my config?

Template deployment uses --keep-vars to preserve dashboard variables and secrets, and applies D1 migrations first. Do not switch a production instance to first-time CLI bootstrap. Back up D1 and SESSION_SECRET and read migration notes before upgrading. Rolling back a Worker does not roll back its database.

Can I use only the CLI?

Yes. Install Node 24 and Bash, clone the repository, and use deploy/v3.example.json to create a config in an ignored directory. Prepare an account-scoped management token, then run npm run deploy:bootstrap -- --config .parcel-v3/deploy.json. See the repository docs for preparation, frozen migration, and rollback.
